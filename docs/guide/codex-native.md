# Native Codex bridge

Native mode connects the web client to an existing Codex daemon. Enable it independently of HAPI's original Codex provider; it does not import conversations or write native messages, settings, queue state or execution state to HAPI's session database.

Configure the hub environment:

```sh
HAPI_CODEX_NATIVE_SOCKET=unix:///path/to/app-server-control.sock
HAPI_CODEX_NATIVE_NAMESPACE=default
HAPI_CODEX_NATIVE_DESKTOP_STATE=/path/to/.codex-global-state.json
HAPI_CODEX_NATIVE_DESKTOP_HOST_ID=remote-ssh-discovered:your-host
```

The namespace is required. Existing HAPI web authentication protects all native data and control routes. The Desktop state/host settings are optional. Without recognizable membership, the normal catalog quietly offers manually selectable interactive candidates and excludes exec, subagent and agent-started records. Known Desktop membership can include legitimate agent-created chats. The optional background catalog is collapsed until requested.

Open the ordinary `/sessions` page. Native conversations appear in HAPI's existing list and open in its existing chat page, header, message renderer and composer. `/codex-native` redirects old bookmarks to `/sessions`. Old imported HAPI links resolve through an explicit endpoint/thread alias. Refresh the metadata list to see new Desktop chats. Opening a conversation attaches to its native ID; it never creates a replacement thread. Attach can load the thread and start its configured MCP integrations, but sends no model input. Other providers retain their existing behavior.

The existing new-session agent selector offers Codex Native alongside Codex and the other agents. A creation choice identifies either a runner machine or a native endpoint; both Codex choices retain the Codex wire flavor. Directory, model, reasoning effort, errors and submission use one form. Runner choices remain visible but disabled when no suitable machine is available. Creating a native conversation explicitly calls the selected daemon. Settings → Machines lists configured native hosts and their connection status. Optional agent names in the session list are controlled by Settings → Display → Sessions; header labels use the existing header metadata settings.

To configure multiple hosts, set `HAPI_CODEX_NATIVE_ENDPOINTS` to a JSON array containing `id`, `label`, `endpoint` and `namespace` for each connection. Optional fields are `token`, `defaultCwd`, `desktopStatePath`, `desktopHostId`, `allowedRoots`, `legacyMachineIds` and `legacyHosts`. The Machines page is currently read-only; connection configuration remains on the hub. Endpoint IDs are stable identities used in URLs; the browser cannot supply arbitrary daemon addresses. Unix sockets and WebSocket endpoints are supported by the transport; each daemon must support the native methods this bridge uses.

History starts at the newest 50 native items. Scrolling upward loads older opaque cursors; the browser retains at most 300 items in the current conversation. Returning to latest replaces the window and cursor together and invalidates pending older requests. Tool details are collapsed. Selected response text can be quoted into the draft. Leaving the conversation drops its browser history cache and releases the native subscription after a five-second grace period. Session-catalog pagination uses endpoint-specific cursors. A bounded aggregate `/sessions?limit=…` is a preview and does not expose cursors that would skip truncated records; endpoint-specific limits apply to the native page itself.

Model and effort controls do not wait for history. Both shortcuts remain visible at phone widths and open the corresponding sections of HAPI's existing settings sheet. Default effort resolves to the selected model's advertised default. Settings confirmation comes from native notifications, or from a fresh native snapshot for an unchanged value; confirmed responses also update the browser cache while SSE reconnects. Settings errors remain visible. Messages enter the native queue directly; ordinary input drains automatically. Interrupted threads explicitly resume the native queue. The bridge does not automatically retry a failed or ambiguous send. A transport error after acceptance can require checking the native conversation before resubmitting.

The existing More menu forwards rename and archive to Codex. Import/sync, stored HAPI export, pins, deletion/reopen and unsupported execution controls are disabled for native conversations. Composer quoting, drafts, model/effort, interrupt and attachments reuse HAPI controls; legacy scheduling, scratchlist and fork/rewind are unavailable. Supported session operations are explicitly declared by the native API adapter; newly added operations require an explicit implementation or classification.

The existing attachment picker, drop and paste controls upload through the selected daemon, including attachment-only messages. Images become native `localImage` inputs; other files are supplied as a filename and daemon-local path. Uploads are staged under `attachments/hapi/<scope>/staging` in the daemon's declared Codex home, with scope binding namespace, endpoint and thread. Sending creates an immutable `sent` copy. Removing a draft only removes staging; previously sent files remain readable. References recover after a hub restart without a hub upload table. Native uploads add no client-side size precheck; infrastructure and daemon errors propagate through the existing attachment interface. Transfer currently uses complete base64 payloads, without streaming.

Assistant file links use the existing file viewer, including source line suffixes. Files and directories are read through the selected daemon, within the thread workspace or configured `allowedRoots`; symlink paths are rejected. The bridge adds no file-viewer or WebSocket frame size limit. The installed `fs/readFile` method has no range parameter, so reading still allocates the complete file. No shell-command fallback is used.

Desktop asynchronous questions remain answerable after their originating turn finishes. Replies use the Desktop envelope and the current active turn ID while running; idle conversations receive a normal native follow-up. Dispatch waits until the current turn state is known, and a failed steer is never automatically retried as a follow-up. Accepted user/steering replies determine whether a question is resolved. Native blocking requests use their original JSON-RPC IDs and remain visible until the daemon resolves them. Command/file approvals and user-input forms are supported; unknown request methods explicitly require the Desktop client. Owner-specific identity verification is not transferred to an arbitrary bridge client. See [protocol evidence](./codex-native-requests.md).

## Previous bridge validation

The design and acceptance criteria are in [the design document](./codex-native-design.md). GPT-6.1 Sol workers implemented the backend and frontend, investigated the protocol and ran integration checks in WSL. The final cross-package run passed 8,623 tests with 14 existing skips; all-package typecheck, fixture generation and web build passed. Subsequent mutation and runtime-state corrections passed all eight focused backend tests, the full hub package (1,426 passed / 3 skipped), four focused web tests, package typechecks and a rebuilt web bundle. All-package typecheck was also repeated successfully during integration. The initial aggregate counts exclude the later-added regressions.

Real read-only checks on M1 verified three continuous native pages, stable repeated cursors, exact native timestamps, idle state, namespace isolation and subscription release. HAPI session/message counts and IDs, and native thread counts and IDs, were unchanged by those read-only checks. The probe used approximately 53 MB RSS.

A separate disposable native conversation verified an actual settings change, unchanged-setting confirmation, cross-connection queue acceptance and completion with the response `OK`. The scratch chats were archived. No user project chat received test input. Desktop async envelope parsing and accepted-answer handling were verified against installed Desktop code and focused tests; a real outstanding Desktop question was not answered during validation.

Browser checks covered the correct four QDP chats, latest M1 response, older-page loading, model/effort hydration, collapsed background catalog and draft quoting at desktop and 390-pixel phone widths. The temporary read-only preview's default Bun idle timeout initially caused reconnects; it was raised above the heartbeat interval. Production already configures a sufficient idle timeout.

The production entry remains the existing HTTPS/Passkey site. Only the hub is enabled; the legacy runner and discovery service remain disabled. The hub has a 1 GiB memory ceiling and no swap allowance. Initial bridge memory was about 71 MB, with a peak near 80 MB; these are startup observations, not a long-duration load benchmark. Previous web builds are backed up under the deployment directory. This mode does not provide the entire Desktop tool and workspace-management interface.

## Existing HAPI interface integration (2026-10-29)

The independent Codex page and message components were removed. Native sessions now use the original `SessionChat`, `SessionHeader`, `HappyThread`, `HappyComposer`, `SessionItem`, creation controls and file viewer. Unsupported controls are capability-gated. A read-only review found and corrected alias injection into catalogs, missing sidebar pagination, lost image-only user messages, known question answers reappearing after cache eviction and missing live-event timestamps.

Verification passed all-package typecheck and the existing package suites: CLI 3,246 passed / 11 skipped; hub 1,435 passed / 3 skipped; web 3,518 passed; shared 329 passed; relay 118 passed. Later native creation/auth corrections passed 17 focused backend tests and hub typecheck. Final all-package typecheck, web suite and production build passed; regenerated fixtures had no drift. The file viewer tests retained their original preview/source/scroll assertions, with the newly required session metadata supplied by their API fixture.

Real WSL checks verified the old M1 alias, exactly four Desktop QDP chats, three continuous item pages, original timestamps, namespace isolation and daemon-backed file/directory reads. A disposable empty conversation verified creation, canonical resolution, SSE, empty items, idle state, a real settings change and archive without model input. HAPI database counts were unchanged by those checks. The daemon does not list an empty unmaterialized conversation before its first user input; the creating connection provides its direct view and settings meanwhile.

Deployment backed up source, web assets and SQLite to `/home/igna/hapi-deployment/backups/native-integrated-20261029T133633Z`. It removed 244,379 obsolete HAPI message rows and cleared the copied execution/settings state, retaining seven minimal URL aliases. The compacted HAPI database is 217,088 bytes. Native history was not modified by that migration.

Historical native image input has a visible image/path placeholder; full native image rendering and Desktop-style plugin mention chips remain presentation limitations.

Browser verification subsequently reproduced two integration failures: comparing an encoded URL to a decoded native session ID selected an empty child outlet, and forwarding raw native reasoning-effort objects to HAPI's string-based model controls threw during rendering. The chat route now uses the router's own match result, and the native adapter converts model records to existing HAPI summaries.

A single component-render regression reproduces the model-catalog failure through the real HAPI chat controls. It passes with the fix, as do web typecheck and the production build. A temporary read-only loopback preview connected to the real WSL daemon verified the old M1 URL, clicking M1 from the ordinary session list, visible latest history and composer, model/effort menus, and opening a response's local-file link in the existing viewer. No model input or settings mutation was submitted during these browser checks.
