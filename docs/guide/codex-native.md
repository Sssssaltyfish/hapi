# Native Codex bridge

Native mode connects the web client to an existing Codex daemon. Enable it independently of HAPI's original Codex provider; it does not import conversations or write native messages, settings, queue state or execution state to HAPI's session database.

Configure the hub environment:

```sh
HAPI_CODEX_NATIVE_SOCKET=unix:///path/to/app-server-control.sock
HAPI_CODEX_NATIVE_NAMESPACE=default
HAPI_CODEX_NATIVE_DESKTOP_STATE=/path/to/.codex-global-state.json
HAPI_CODEX_NATIVE_DESKTOP_HOST_ID=remote-ssh-discovered:your-host
```

The namespace is required. Existing HAPI web authentication protects all native data and control routes. Each endpoint can optionally specify one Desktop state file and its host ID within that Desktop (`local` or a remote host). Endpoints can share a Desktop file or use separate files. When a daemon supplies a project ID it takes precedence. For older chats without one, HAPI uses the configured Desktop's assignments, workspace roots and worktree information. With no Desktop configuration, an unassigned chat appears under No workspace. If a previously configured file becomes unreadable, HAPI keeps the last known group. Native project actions use the daemon's canonical project IDs. Exec and subagent records appear in a separate background group for each machine; that group remains collapsed until requested.

Open the ordinary `/sessions` page. Chosen native conversations appear in HAPI's existing list and open in its existing chat page, header, message renderer and composer. `/codex-native` redirects old bookmarks to `/sessions`. Old imported HAPI links resolve through an explicit endpoint/thread alias. Use the existing-chat picker to choose individual chats or a workspace. Opening a conversation attaches to its native ID; it never creates a replacement thread. Attach can load the thread and start its configured MCP integrations, but sends no model input. Other providers retain their existing behavior.

The existing new-session agent selector offers Codex Native alongside Codex and the other agents. A creation choice identifies either a runner machine or a native endpoint; both Codex choices retain the Codex wire flavor. Directory, model, reasoning effort, errors and submission use one form. Selecting Native preserves runner-machine selection and availability discovery, so the user can switch back while setup is loading or no runner is connected. Creation still requires a suitable connected target. Settings → Machines presents both types of machines together. Optional agent names in the session list are controlled by Settings → Display → Sessions; header labels use the existing header metadata settings.

Settings → Machines can add native connections and rename existing ones using the same inline name editor as runner machines. Rows show the sanitized connection address, the operating system reported by the daemon and connection status. The shared Machine field in the creation form lists the appropriate targets for the selected provider. A runner registers itself with HAPI; an existing Codex daemon has no equivalent HAPI registration method, so the Hub connects to its configured Unix socket or WebSocket address. This does not launch another runner or daemon.

Native connection metadata uses the Hub's existing atomic, locked `settings.json` storage with owner-only permissions. Added connections receive stable server-generated IDs and the authenticated namespace. Display-name changes preserve those IDs and active subscriptions. API responses never include connection tokens. Existing environment configuration remains available: `HAPI_CODEX_NATIVE_ENDPOINTS` accepts a JSON array containing `id`, `label`, `endpoint` and `namespace`; optional fields are `token`, `defaultCwd`, `desktopStatePath`, `desktopHostId`, `fileAccess` (`workspace` or `host`), `allowedRoots`, `legacyMachineIds` and `legacyHosts`. Environment-managed connections can be renamed in the UI. Address editing and deletion are not provided; add a separate connection for a different daemon. Each daemon must support the native methods this bridge uses.

In Settings → Machines, a Desktop connection shows Windows Desktop, macOS Desktop or Linux Desktop. HAPI uses the platform of the `local` daemon associated with the same Desktop state file and namespace. A remote target can therefore show a different daemon platform. If no local endpoint is configured, set `desktopPlatform` (`windows`, `macos` or `linux`) in the endpoint configuration, or `HAPI_CODEX_NATIVE_DESKTOP_PLATFORM` for a single endpoint. With no platform information, the label is Codex Desktop.

## Choosing chats and workspaces

The home list saves display choices for each namespace and native machine. Each workspace initially shows the configured number of preview rows. Expand or collapse it in batches using the same controls as other providers. The picker loads project and chat metadata in pages as you expand a machine or workspace; it does not load conversation history. Choosing a whole workspace discovers its members progressively. Hiding a chat or workspace changes HAPI's display choice and does not archive or delete the Codex entity. Moving a chat to another workspace or clearing its workspace uses the daemon's project assignment; it does not silently rewrite the chat's working directory or reasoning effort.

While a home or picker page is open, a shared directory connection receives native changes and local display-choice notifications. If all viewers leave, that connection closes. A later connection shows the cached list immediately and refreshes metadata for already known chats and workspaces in the background. This repairs missed moves and renames for known chats without opening their history. Another browser joining an already healthy connection shares that observer and does not start the same refresh again.

Workspace membership is discovered lazily rather than kept as a strict live mirror of every historical member. Reconnecting does not enumerate every workspace or discover previously unknown historical chats. If Desktop moved a chat that HAPI had never discovered into a chosen workspace while HAPI was disconnected, explicitly re-import or refresh that whole workspace to discover the changed membership. Known chat moves and name changes are reconciled separately. A failed metadata read preserves the cached display choice until a later successful refresh.

History starts at the newest 50 native items. Scrolling upward loads older opaque cursors; the browser retains at most 300 items in the current conversation. Returning to latest replaces the window and cursor together and invalidates pending older requests. Tool details are collapsed. Browser memory retains a bounded set of recent history windows and reading anchors so visiting a file does not reset the conversation to the bottom; the native subscription still releases after a five-second grace period. A separate bounded prompt index pages older history without adding every tool record to the rendered transcript. Selecting an indexed prompt loads its original page and locates the actual message. Session-catalog pagination uses endpoint-specific cursors. A bounded aggregate `/sessions?limit=…` is a preview and does not expose cursors that would skip truncated records; endpoint-specific limits apply to the native page itself.

Model and effort controls do not wait for history. Both shortcuts remain visible at phone widths and open the corresponding sections of HAPI's existing settings sheet. Default effort resolves to the selected model's advertised default. Settings confirmation comes from native notifications, or from a fresh native snapshot for an unchanged value; confirmed responses also update the browser cache while SSE reconnects. Settings errors remain visible. Messages enter the native queue directly; ordinary input drains automatically. Interrupted threads explicitly resume the native queue. The bridge does not automatically retry a failed or ambiguous send. A transport error after acceptance can require checking the native conversation before resubmitting.

The existing More menu forwards rename and archive to Codex. Stored HAPI export, pins, deletion/reopen and unsupported execution controls are disabled for native conversations. Existing-chat selection and workspace display choices follow the separate directory behavior described above. Composer quoting, drafts, model/effort, interrupt and attachments reuse HAPI controls; legacy scheduling, scratchlist and fork/rewind are unavailable. Supported session operations are explicitly declared by the native API adapter; newly added operations require an explicit implementation or classification.

Native session settings expose the approval reviewer (`user` or `auto_review`) separately from when approval is requested (`on-request`, `untrusted`, or `never`). Updating either sends only that field and preserves the daemon's sandbox and any granular policy. The existing sandbox is displayed, and changes apply to subsequent turns after daemon confirmation. Runner sessions retain their provider-specific permission modes, further restricted by any advertised session capabilities; Native does not reuse runner permission presets that also change filesystem access.

The quote button follows the selected response text. Codex and Native use the Desktop response-annotations envelope, displayed as removable quote cards beside an ordinary draft body. Native source metadata includes the original response item ID and rendered-text offsets only when the selection has a reliable single source; otherwise the optional source is omitted. Other providers retain Markdown blockquotes. Async question replies render the question and answer while preserving their original wire envelope. Native subagent activity is projected into HAPI's existing agent cards using actual child thread IDs; completing an activity record does not by itself complete the child run.

The existing attachment picker, drop and paste controls upload through the selected daemon, including attachment-only messages. Images become native `localImage` inputs; other files are supplied as a filename and daemon-local path. Uploads are staged under `attachments/hapi/<scope>/staging` in the daemon's declared Codex home, with scope binding namespace, endpoint and thread. Sending creates an immutable `sent` copy. Removing a draft only removes staging; previously sent files remain readable. References recover after a hub restart without a hub upload table. Native uploads add no client-side size precheck; infrastructure and daemon errors propagate through the existing attachment interface. Transfer currently uses complete base64 payloads, without streaming.

Assistant file links use the existing file viewer, including source line suffixes. Authenticated file and directory reads go through the selected daemon. Each endpoint's server-side `fileAccess` setting defaults to `workspace`, restricting reads to the thread workspace and configured `allowedRoots` and rejecting symlinks. Set it to `host` to allow outside-workspace paths and symbolic links according to the daemon's filesystem permissions. For a single endpoint configured with `HAPI_CODEX_NATIVE_SOCKET`, use `HAPI_CODEX_NATIVE_FILE_ACCESS=host`. This policy is not exposed as a browser setting. Relative paths resolve from the thread's working directory. Explicit file links accept artifact extensions beyond the prose autolink list. Text, Markdown and supported images open in the existing viewer; files that cannot be previewed download automatically once, with the existing download button available for retry. The bridge adds no file-viewer or WebSocket frame size limit. The installed `fs/readFile` method has no range parameter, so reading still allocates the complete file. No shell-command fallback is used.

The existing composer suggestion list supports `@` workspace files and folders, installed enabled plugins returned by `plugin/list`, and accessible enabled apps returned by `app/list`. Skills use HAPI's existing leading `$skill` syntax and the daemon's `skills/list`. File paths remain quoted text so the model receives them; app/plugin references and skills use their native input types. Discovery results are disposable and bounded, and superseded browser queries cannot overwrite newer suggestions. A daemon that does not return a supported target contributes no suggestions of that type.

Desktop asynchronous questions remain answerable after their originating turn finishes. Replies use the Desktop envelope and the current active turn ID while running; idle conversations receive a normal native follow-up. Dispatch waits until the current turn state is known, and a failed steer is never automatically retried as a follow-up. Accepted user/steering replies determine whether a question is resolved. Native blocking requests use their original JSON-RPC IDs and remain visible until the daemon resolves them. Command/file approvals and user-input forms are supported; unknown request methods explicitly require the Desktop client. Owner-specific identity verification is not transferred to an arbitrary bridge client. See [protocol evidence](./codex-native-requests.md).

## Previous bridge validation

The design and acceptance criteria are in [the design document](./codex-native-design.md). GPT-6.1 Sol workers implemented the backend and frontend, investigated the protocol and ran integration checks in WSL. The final cross-package run passed 8,623 tests with 14 existing skips; all-package typecheck, fixture generation and web build passed. Subsequent mutation and runtime-state corrections passed all eight focused backend tests, the full hub package (1,426 passed / 3 skipped), four focused web tests, package typechecks and a rebuilt web bundle. All-package typecheck was also repeated successfully during integration. The initial aggregate counts exclude the later-added regressions.

Real read-only checks on M1 verified three continuous native pages, stable repeated cursors, exact native timestamps, idle state, namespace isolation and subscription release. HAPI session/message counts and IDs, and native thread counts and IDs, were unchanged by those read-only checks. The probe used approximately 53 MB RSS.

A separate disposable native conversation verified an actual settings change, unchanged-setting confirmation, cross-connection queue acceptance and completion with the response `OK`. The scratch chats were archived. No user project chat received test input. Desktop async envelope parsing and accepted-answer handling were verified against installed Desktop code and focused tests; a real outstanding Desktop question was not answered during validation.

Browser checks covered the correct four QDP chats, latest M1 response, older-page loading, model/effort hydration, collapsed background catalog and draft quoting at desktop and 390-pixel phone widths. The temporary read-only preview's default Bun idle timeout initially caused reconnects; it was raised above the heartbeat interval. Production already configures a sufficient idle timeout.

The production entry remains the existing HTTPS/Passkey site. Only the hub is enabled; the legacy runner and discovery service remain disabled. The hub has a 1 GiB memory ceiling and no swap allowance. Initial bridge memory was about 71 MB, with a peak near 80 MB; these are startup observations, not a long-duration load benchmark. Previous web builds are backed up under the deployment directory. This mode does not provide the entire Desktop tool and workspace-management interface.

## Desktop and CLI message context

HAPI projects recognized context envelopes into its existing chat controls while retaining the original Codex message. Desktop local file mentions appear as compact filename references using the existing file viewer and source-line navigation. Context sections retain their original order, followed by the request. Copying the message includes context content, filenames, paths, source lines and request.

| Verified input | HAPI presentation |
| --- | --- |
| Desktop `# Files mentioned by the user:` with local absolute paths, optional `(line N)` / `(lines N-M)`, and the complete Desktop attachment instruction footer | Filename references; clicking opens the existing file viewer at the first selected line. Windows paths and paths containing spaces are preserved. |
| Desktop IDE context with an active local file and/or open local tabs, without an active selection | Collapsed IDE summary with the original active file and tab order; expanding it shows the existing file references. |
| Desktop local pasted-text files with JSON-quoted preview labels | Existing file references under Pasted text. A pasted-text-only request keeps its request-in-pasted-text indicator. |
| Desktop basic worktree setup instructions | Collapsed Worktree setup summary; expanding retains the complete setup instruction. |
| Desktop response annotations with selected text and optional comments | Existing quote cards and source navigation when source metadata is available. |
| Desktop referenced Codex chats with validated host/thread IDs | Existing thread links in the request; the model-facing reference instructions are omitted from display. |
| Desktop asynchronous question replies | Existing question and answer presentation. |
| Desktop complete scheduled heartbeat envelopes | Existing scheduled-message cards. |
| Existing HAPI generic CLI grammar: command name, arguments, stdout and stderr tags | Existing CLI command/output presentation. This is HAPI's accepted grammar; it is not a claim that Codex CLI emits these tags. |

Uploaded-file pointers, Source Files IDs, Library/shared-thread metadata, browser/page/app context, PR repair/check context and diff/browser comments remain visible as context text. IDE active selections and standalone selected-text sections contain unescaped source text without a reliable closing boundary; the entire ambiguous section stays visible. Worktree sections with starting-state extensions also stay visible until those variants have a validated presentation. A file or pasted-text section containing unsupported metadata or an upload variant remains visible in full. This keeps unfamiliar context and user prose available while those integrations are developed.

Only recognized leading context sections are projected. Quoted examples, fenced examples, malformed sections and unknown members stay visible. Parsing stops at the actual request, so a user-authored `## My request:` heading or another context example in that request is retained. The presentation conversion does not alter queued input, daemon history or the context received by the model.

## Tool details and conversation titles

Native file changes show each file's path, diff and execution status. Optional
stdout/stderr are displayed when the daemon includes them. Some daemon versions
omit those streams and wait-for-agent arguments/results from paged history;
HAPI does not read rollout files to reconstruct them. Short collaboration
receipts remain compact and can join tool groups; calls with additional details
use the existing tool detail view. There is no extra persistent output cache.

New native conversations created in HAPI generate a title asynchronously after
their first accepted text message. A separate ephemeral, tool-disabled daemon
thread summarizes the request; HAPI then writes the title with `thread/name/set`
only while the conversation is still unnamed. Explicit renames take precedence.
The existing name event updates the list, open conversation and browser tab.
The title request does not change the source conversation's model or effort.

## Conversation recap and the Codex CLI

Native and managed Codex sessions use the CLI's ephemeral helper workflow for `/recap`. HAPI reads bounded recent history, selects visible user and assistant exchanges in order, and uses a separate helper thread with the same model, provider and working directory. The helper disables tools, MCP servers, hooks, plugins, memories and skills. It produces a structured summary and optional next action in the user's language; its ephemeral thread is detached after completion and is not adopted as a HAPI session.

The [official CLI implementation](https://github.com/openai/codex/blob/94ca55a93c11348c6e3431e292b8e9a33dfefc82/codex-rs/tui/src/app/recap.rs) orchestrates the same [temporary structured request](https://github.com/openai/codex/blob/94ca55a93c11348c6e3431e292b8e9a33dfefc82/codex-rs/tui/src/temporary_structured_request.rs) in its frontend. The daemon has no dedicated `/recap` RPC. HAPI reuses the upstream prompt and output bounds: at most 32,768 UTF-8 prompt bytes, a summary of at most 700 characters, and a nullable next action of at most 200 characters. Long history fields retain both ends. Tool output and private reasoning are excluded.

The source must be idle when history is captured. The recap stays bound to that source turn and completes even if the source advances during generation. HAPI validates the helper's structured response and interrupts only the helper on explicit cancellation or timeout before detaching it. Unsupported hosts return an upgrade explanation. The command does not compact, fork, or submit input to the original conversation.

`thread/sample` is a separate public experimental native API and is no longer used by HAPI's recap command. Read-only nonexistent-thread probes on 2026-11-06 confirmed that the running WSL daemon `0.165.0-alpha.1.2` and Windows daemon `0.166.0-alpha.5.1` recognize that method; the historical unknown-variant report does not establish their current method recognition. Details of the recap behavior and verification are in [Remote provider command capabilities](../remote-provider-commands.md).
